# Payment Service

Simulated payment processing for MyCima reservation holds. It is an independent
FastAPI microservice that exposes both a REST API and the gRPC service
`nocturne.payment.PaymentService` over the same business logic.

The service owns its own `payments` database. It never reads or writes the
database of the User, Reservation, Movie or Notification services.

> **Security invariant:** the amount charged is always the authoritative total
> returned by the Reservation Service for the supplied `hold_id`. Any amount sent
> by a client (REST or gRPC) is ignored or rejected. No real card data, CVV or
> banking credential is ever collected, transmitted or stored.

---

## 1. Purpose

The service turns a temporary reservation hold into a paid booking:

1. Authenticate the caller with the repository's shared JWT.
2. Load the hold from the Reservation Service and verify ownership and expiry.
3. Charge the hold's authoritative total with a deterministic simulator.
4. Confirm the same hold with the Reservation Service using the payment's
   transaction reference.
5. Expose payment history to users and refunds/statistics to administrators.

It demonstrates practical distributed-system concerns: a service-owned database,
idempotent request handling, duplicate-charge prevention under concurrency,
retryable cross-service confirmation, and failure isolation between charging and
reservation confirmation.

## 2. Architecture

```
                 ┌──────────────────────────────┐
   HTTP + JWT    │          Gateway             │
  ──────────────▶│  (existing, not modified)    │
                 └──────────────┬───────────────┘
                                │ /api/payments, /api/admin/payments
                                ▼
┌──────────────────────────────────────────────────────────────┐
│                    payment-service (this repo dir)           │
│                                                              │
│  REST routers ──┐                                            │
│                 ├──▶ PaymentService (shared business logic)  │
│  gRPC servicer ─┘         │                 │                │
│                           │                 │                │
│                    SQLAlchemy 2.x      httpx.AsyncClient     │
│                           │                 │                │
│                           ▼                 ▼                │
│                    payments_db      Reservation Service      │
│                    (PostgreSQL)     GET  /holds/{id}         │
│                                     POST /holds/{id}/confirm  │
└──────────────────────────────────────────────────────────────┘
```

One Uvicorn process serves both transports:

- REST (FastAPI) on port `8000` by default.
- gRPC (`grpc.aio`) on port `50051` by default.

REST and gRPC share `app/services/payment_service.py`; the transports only handle
authentication extraction, input validation and error mapping.

Key design decisions:

- **Amount trust boundary.** REST forbids an `amount` field in the JSON body.
  gRPC accepts the protobuf field but never reads it.
- **Money is `Decimal`.** The database column is `NUMERIC(10,2)`; JSON returns a
  fixed two-decimal string.
- **No transaction spans a network call.** Each database step is a short,
  committed session.
- **Database constraints are the final concurrency guard.** `hold_id` is unique,
  so two simultaneous requests cannot both charge the same hold.
- **Confirmation is a separate step.** A failed or unavailable Reservation
  Service never reverses an already successful charge.

## 4. REST API

All paths are shown **without** the gateway's `/api` prefix. Through the gateway,
`GET /api/payments` reaches `GET /payments` here.

Authentication is `Authorization: Bearer <JWT>`. The JWT must be issued by the
User Service with the shared `JWT_SECRET`; the numeric user id is in `sub`.

`POST /payments` additionally requires an `Idempotency-Key` header containing
1–128 printable ASCII characters.

### `POST /payments`

Create and process one payment.

```json
{
  "hold_id": "3ef1f6bd-6e1d-4a4a-bfd9-3c0f4e88e6c0",
  "method": "CARD",
  "currency": "MAD"
}
```

- `hold_id` (required): reservation hold UUID.
- `method` (required): `CARD` or `WALLET`.
- `currency` (optional): three-letter code checked against
  `SUPPORTED_CURRENCIES`; defaults to `DEFAULT_CURRENCY` (`MAD`).
- `simulate_outcome` (optional): `success` or `failure`; accepted **only** when
  `PAYMENT_SIMULATION_ENABLED=true`. Otherwise the request is rejected with 422.
- `amount` is **not** an accepted field. Extra fields are forbidden, so sending
  one returns 422.

Responses:

| Status | Meaning |
|---|---|
| `201 Created` | New payment created and processed (success or simulated failure) |
| `200 OK` | Idempotent replay of an existing payment |
| `400` | Missing `Idempotency-Key` |
| `401` | Missing, malformed, expired or wrongly signed JWT |
| `404` | Hold does not exist or is not owned by the caller |
| `409` | Hold already has a payment, or the idempotency key belongs to a different request |
| `410` | Hold expired |
| `422` | Validation error, unsupported method/currency, simulation disabled |
| `503` | Reservation Service unavailable before the charge |

Example response (`201`):

```json
{
  "id": "d8c4f0d0-8f0e-4a55-9f4f-8f1c3f6e4b2a",
  "user_id": 42,
  "hold_id": "3ef1f6bd-6e1d-4a4a-bfd9-3c0f4e88e6c0",
  "amount": "24.00",
  "currency": "MAD",
  "status": "SUCCEEDED",
  "method": "CARD",
  "transaction_ref": "pay_9b0b6e0c1f4f4f4a9c8f6d8e5c3a2b10",
  "failure_reason": null,
  "confirmation_status": "CONFIRMED",
  "confirmation_error": null,
  "confirmation_attempted_at": "2026-11-15T15:20:00.123456+00:00",
  "created_at": "2026-11-15T15:20:00.100000+00:00",
  "updated_at": "2026-11-15T15:20:00.123456+00:00",
  "processed_at": "2026-11-15T15:20:00.110000+00:00",
  "refunded_at": null
}
```

### `GET /payments`

Return only the authenticated user's payments, newest first.

Query parameters: `status` (one of the six statuses), `limit` (1–200, default 50),
`offset` (default 0).

```json
{
  "items": [ { "...": "PaymentOut" } ],
  "total": 1,
  "limit": 50,
  "offset": 0
}
```

### `GET /payments/{payment_id}`

Return one payment if it belongs to the caller. A payment owned by somebody else
and a non-existent payment both return `404` (no ownership enumeration).

### `POST /payments/{payment_id}/retry-confirmation`

Retry only the Reservation Service confirmation for an already successful
payment. It never creates a new payment, never calls the Reservation Service's
hold lookup, and reuses the original `transaction_ref` as `payment_ref`.

- `200`: refreshed payment (confirmation may now be `CONFIRMED`, still `PENDING`,
  or `FAILED` for a permanently rejected hold).
- `404`: payment does not exist or belongs to another user.
- `409`: payment is not `SUCCEEDED` (nothing to confirm).
- `503`: Reservation Service is still unavailable; the successful charge is kept.

### `GET /admin/payments`

Administrator only. Same list shape as `GET /payments`, with filters `user_id`,
`status`, `method`, `currency`, `hold_id`, `limit`, `offset`.

### `POST /admin/payments/{payment_id}/refund`

Administrator only. Simulated full refund.

- `200`: payment is `REFUNDED` (idempotent for an already refunded payment).
- `404`: unknown payment.
- `409`: payment is not `SUCCEEDED` (for example `FAILED` or `PENDING`).

The refund is a local simulation. It does **not** cancel a booking in the
Reservation Service (see limitations).

### `GET /admin/stats`

Administrator only.

```json
{
  "total_payments": 12,
  "by_status": {
    "PENDING": 0,
    "PROCESSING": 0,
    "SUCCEEDED": 9,
    "FAILED": 2,
    "REFUND_PENDING": 0,
    "REFUNDED": 1
  },
  "by_method": {"CARD": 8, "WALLET": 4},
  "by_currency": {"MAD": 12},
  "succeeded_count": 9,
  "failed_count": 2,
  "refunded_count": 1,
  "pending_confirmations": 0,
  "gross_amount": "288.00",
  "refunded_amount": "24.00",
  "net_amount": "264.00"
}
```

### `GET /health`

Returns `200` when the database responds and gRPC is running (or explicitly
disabled), otherwise `503` with `"status": "degraded"`.

```json
{"status": "ok", "service": "payment-service", "database": "up", "grpc": "up"}
```

### Error format

All application errors use FastAPI's standard shape:

```json
{"detail": "Payment not found."}
```

Internal exception text, SQL, secrets and upstream response bodies are never
returned to clients.

## 5. gRPC API

The exact supplied contract is preserved in `proto/payment.proto`:

```protobuf
syntax = "proto3";

package nocturne.payment;

service PaymentService {
  rpc Charge (ChargeRequest) returns (ChargeResponse);
}

message ChargeRequest {
  string hold_id = 1;
  string amount = 2;
  string currency = 3;
}

message ChargeResponse {
  string transaction_id = 1;
  string status = 2;
  string failure_reason = 3;
  string amount = 4;
  string currency = 5;
  string processed_at = 6;
}
```

Default endpoint: `0.0.0.0:50051` (`GRPC_HOST`, `GRPC_PORT`).

### Authentication

The JWT is passed in gRPC metadata, not in the message:

```
authorization: Bearer <JWT>
```

The service rejects calls without a valid token with `UNAUTHENTICATED`. User ids
supplied in metadata (for example `x-user-id`) are ignored.

### Method selection

The protobuf contract has no payment-method field. The gRPC method defaults to
`GRPC_DEFAULT_METHOD` (`CARD`) and can be overridden with optional metadata:

```
x-payment-method: WALLET
```

### Amount handling

`ChargeRequest.amount` is **untrusted and ignored**. The response `amount` is the
authoritative total returned by the Reservation Service. A client that sends
`0.01` for a `73.25` hold is charged `73.25`.

### Status mapping

| Condition | gRPC status |
|---|---|
| Missing/invalid/expired JWT | `UNAUTHENTICATED` |
| Invalid UUID, bad currency/method | `INVALID_ARGUMENT` |
| Unknown hold or another user's hold | `NOT_FOUND` |
| Expired/released hold, duplicate conflict | `FAILED_PRECONDITION` |
| Reservation Service unavailable | `UNAVAILABLE` |
| Unexpected internal error | `INTERNAL` (generic message) |

A simulated payment decline is **not** a gRPC error: it returns a normal
`ChargeResponse` with `status = "FAILED"` and a safe `failure_reason`.

Because the contract has no idempotency key, `hold_id` is the replay key: calling
`Charge` twice for the same hold returns the same `transaction_id` and does not
charge twice.

### Calling `PaymentService.Charge` from another microservice

```python
import grpc
import payment_pb2
import payment_pb2_grpc


def charge_hold(hold_id: str, user_jwt: str, currency: str = "MAD") -> dict:
    with grpc.insecure_channel("payment-service:50051") as channel:
        stub = payment_pb2_grpc.PaymentServiceStub(channel)
        response = stub.Charge(
            payment_pb2.ChargeRequest(
                hold_id=hold_id,
                amount="0.01",   # ignored by design
                currency=currency,
            ),
            metadata=(("authorization", f"Bearer {user_jwt}"),),
            timeout=10,
        )
        return {
            "transaction_id": response.transaction_id,
            "status": response.status,
            "failure_reason": response.failure_reason,
            "amount": response.amount,
            "currency": response.currency,
            "processed_at": response.processed_at,
        }
```

The caller must send the **end user's** JWT, because the Reservation Service
verifies hold ownership with that same token.

## 6. Database schema

The service creates its table at startup (`Base.metadata.create_all`). It does
not run migrations yet; see limitations.

Table `payments`:

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key, generated by the service |
| `user_id` | BIGINT | JWT subject, indexed |
| `hold_id` | UUID | **Unique**; one payment per reservation hold |
| `amount` | NUMERIC(10,2) | Authoritative hold total, `>= 0` |
| `currency` | VARCHAR(3) | Validated code, length 3 |
| `status` | VARCHAR(24) | Check constraint on the six allowed values |
| `method` | VARCHAR(12) | Check constraint: `CARD`, `WALLET` |
| `transaction_ref` | VARCHAR(64) | **Unique**, nullable until success |
| `idempotency_key` | VARCHAR(128) | **Unique**, nullable for gRPC |
| `request_fingerprint` | VARCHAR(64) | SHA-256 of the request identity |
| `failure_reason` | TEXT | Safe, client-facing reason |
| `confirmation_status` | VARCHAR(16) | `NOT_REQUIRED`, `PENDING`, `CONFIRMED`, `FAILED` |
| `confirmation_error` | TEXT | Last confirmation error category |
| `confirmation_attempted_at` | TIMESTAMPTZ | Last confirmation attempt |
| `created_at` | TIMESTAMPTZ | Creation time |
| `updated_at` | TIMESTAMPTZ | Last update time |
| `processed_at` | TIMESTAMPTZ | When the charge reached a terminal status |
| `refunded_at` | TIMESTAMPTZ | When the simulated refund completed |

Constraints and indexes:

- `UNIQUE (hold_id)` — prevents two charges for one hold.
- `UNIQUE (idempotency_key)` — prevents duplicate REST retries (NULL allowed).
- `UNIQUE (transaction_ref)` — prevents accidental reference reuse.
- `CHECK` constraints for `status`, `method`, `confirmation_status`,
  `amount >= 0`, `length(currency) = 3`.
- `(user_id, created_at)` and `(status, created_at)` composite indexes.
- Index on `status` and on `user_id` for filtered lookups.

Status values: `PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `REFUND_PENDING`,
`REFUNDED`.

Money is always `Decimal` in Python. No floating-point arithmetic is used for
amounts.

## 8. Installation

Requirements: Python 3.12+ (3.14 is also tested locally), pip, and optionally
Docker for PostgreSQL.

```powershell
cd payment-service
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
```

`requirements-dev.txt` adds `pytest` and `grpcio-tools`. Regenerate the protobuf
modules only if the contract changes:

```powershell
python -m grpc_tools.protoc -I proto --python_out=generated --grpc_python_out=generated proto/payment.proto
```

The generated files pin the runtime versions they need; `requirements.txt`
currently requires `grpcio>=1.81.2` and `protobuf>=6.33.5,<7.0`.

```powershell
$env:DATABASE_URL = "sqlite:///C:/Users/me/payment_dev.db"
```

- REST/docs: <http://localhost:8000/docs>
- gRPC: `localhost:50051`
- Health: <http://localhost:8000/health>

```powershell
docker compose -f docker-compose.dev.yml up -d
```

`RESERVATION_SERVICE_URL` at your teammate's instance; without it, creating a
payment correctly returns `503` and writes no payment row.

## 11. Tests

```powershell
cd payment-service
.\.venv\Scripts\python.exe -m pytest
```

The suite is self-contained:

- A throwaway SQLite file database is created in the system temp directory.
- The Reservation Service is replaced by an in-memory fake (`FakeReservationClient`),
  so no network access or teammate service is required.
- JWTs are signed with a test secret.
- gRPC tests start a real loopback `grpc.aio` server on an ephemeral port.

Coverage includes:

- Successful CARD/WALLET payment, authoritative amount retrieval, confirmation.
- Simulated failure, no confirmation, recorded failure reason.
- Missing/malformed/expired/wrong-secret JWT and non-numeric `sub`.
- Unknown hold, expired hold, clock-expired hold, released hold.
- Another user's hold and another user's payment (ownership isolation).
- Client-supplied `amount` rejection (REST) and ignoring (`gRPC`).
- Unsupported currency and payment method.
- Simulation controls rejected when disabled.
- Idempotent replay, same key + different request → 409, duplicate hold → 409.
- Concurrent same-key requests (200 + 201, one row), concurrent different-key
  requests (201 + 409, one row).
- Direct database unique-constraint enforcement for `hold_id` and
  `idempotency_key`.
- Reservation Service unavailable before charging (503, no row).
- Confirmation failure after success (kept `SUCCEEDED`), retry without a new
  charge, duplicate retries.
- Admin-only refund (idempotent), admin list/filter and stats.
- Reservation HTTP client: Bearer forwarding, authoritative total parsing,
  upstream status-to-exception mapping (404/410/409/401/500/503), timeout
  handling, malformed payload rejection, and `payment_ref` confirmation body.
- gRPC success, failure response, auth failures, invalid/unknown/expired hold,
  unavailable dependency, duplicate hold replay, metadata user-id spoofing.

Latest local result: **54 passed**.

Tests run against SQLite for speed and isolation. The schema uses portable
unique/check constraints and the direct constraint test exercises them, but a
full PostgreSQL integration run (for example `DATABASE_URL` against the dev
Compose database) is not part of the automated suite. Docker was installed in the
development environment but its daemon was not running during the final check, so
the PostgreSQL path is documented but was not executed here.

## 12. Example REST requests

Obtain a token from the User Service (through the gateway or directly):

```powershell
$login = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/auth/login `
  -ContentType application/json `
  -Body '{"email":"user@example.com","password":"secretpass1"}'
$token = $login.access_token
```

REST calls go through the gateway in the real system. The examples below use
`/api`, which the gateway strips before forwarding.

Create a hold (Reservation Service through the gateway):

```powershell
$hold = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/holds `
  -Headers @{ Authorization = "Bearer $token" } `
  -ContentType application/json `
  -Body '{"showtime_id":1,"seats":["A1","A2"]}'
```

Pay:

```powershell
$payment = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/payments `
  -Headers @{
    Authorization = "Bearer $token"
    "Idempotency-Key" = [guid]::NewGuid().ToString()
  } `
  -ContentType application/json `
  -Body (@{
    hold_id = $hold.id
    method = "CARD"
    currency = "MAD"
  } | ConvertTo-Json)
```

List, read and retry confirmation:

```powershell
Invoke-RestMethod -Uri http://localhost:8000/api/payments `
  -Headers @{ Authorization = "Bearer $token" }

Invoke-RestMethod -Uri "http://localhost:8000/api/payments/$($payment.id)" `
  -Headers @{ Authorization = "Bearer $token" }

Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8000/api/payments/$($payment.id)/retry-confirmation" `
  -Headers @{ Authorization = "Bearer $token" }
```

Admin refund and statistics:

```powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8000/api/admin/payments/$($payment.id)/refund" `
  -Headers @{ Authorization = "Bearer $adminToken" }

Invoke-RestMethod -Uri http://localhost:8000/api/admin/payments/stats `
  -Headers @{ Authorization = "Bearer $adminToken" }
```

> The service itself exposes `GET /admin/stats`. Because the Reservation Service
> already owns `/api/admin/stats`, the gateway should rewrite
> `/api/admin/payments/stats` to this service's `/admin/stats` (see 17.3).

Error example — same key, different request:

```json
{"detail": "This Idempotency-Key was already used for a different request."}
```

## 13. Example gRPC client usage

Generate a client from the same `proto/payment.proto`, then:

```python
import grpc
```

## 14. Payment workflow

1. **Authenticate.** REST reads the Bearer token; gRPC reads the `authorization`
   metadata entry. The shared JWT is verified and the numeric user id is taken
   from `sub`. A client-supplied user id is never used.
2. **Validate input.** `hold_id` must be a UUID; method must be `CARD`/`WALLET`;
   currency must be in the allow-list. REST requires `Idempotency-Key`.
3. **Check for an earlier attempt.** A matching idempotency key or hold id is
   resolved before any network call.
4. **Load the hold.** `GET {RESERVATION_SERVICE_URL}/holds/{hold_id}` with the
   caller's token. No database transaction is open.
5. **Verify ownership and state.** The hold `user_id` must equal the JWT subject;
   status must be `active`; `expires_at`/`seconds_left` must still be valid.
   Another user's hold is reported as `404`, not `403`.
6. **Take the authoritative amount.** `total` from the hold is converted to a
   two-decimal `Decimal`; the client's amount is never consulted.
7. **Insert `PENDING`.** A short transaction inserts the payment and commits.
   Unique constraints on `idempotency_key`/`hold_id` decide concurrent winners.
8. **Process.** The record moves to `PROCESSING`, the deterministic simulator
   decides success/failure, then the row becomes `SUCCEEDED` with a unique
   `transaction_ref`, or `FAILED` with a safe reason.
9. **Confirm the reservation.** Only after a successful commit, call
   `POST /holds/{hold_id}/confirm` with `{"payment_ref": transaction_ref}`.
   - Success sets `confirmation_status = CONFIRMED`.
   - Temporary failure keeps `SUCCEEDED` and sets `PENDING`; the client can call
     `retry-confirmation`.
   - Permanent rejection (expired/released hold) sets `FAILED` with a safe reason.
10. **Return the payment.** REST returns `201` for a new payment and `200` for a
    replay; gRPC returns `ChargeResponse`.

Statuses:

- `PENDING` → `PROCESSING` → `SUCCEEDED` or `FAILED`
- `SUCCEEDED` → `REFUND_PENDING` → `REFUNDED` (administrator simulation)

## 15. Security considerations

- **JWT only.** Signatures and expiry are verified by the repository's
  `shared.auth.decode_access_token`; the algorithm comes from
  `JWT_ALGORITHM`.
- **Ownership.** User endpoints filter by the token subject. Another user's
  payment or hold is indistinguishable from a missing one (`404`).
- **Admin role.** Admin routes require `role == "admin"` in the verified token,
  consistent with the other services in this repository. The token is trusted,
  not re-checked against the User Service on every request.
- **No client amounts.** REST rejects an `amount` field; gRPC ignores it.
- **No sensitive payment data.** Only `CARD`/`WALLET` labels are stored. Card
  numbers, CVVs, expiry dates and holder names are never accepted or logged.
- **Signed transaction references.** `transaction_ref` is generated server-side
  (`pay_<uuid hex>`), unique in the database, and used as the reservation
  `payment_ref`.
- **No internal leakage.** Upstream response bodies and exceptions are not
  forwarded; the gRPC layer returns a generic `INTERNAL` message.
- **Simulation guards.** Request-controlled success/failure is rejected unless
  `PAYMENT_SIMULATION_ENABLED=true`. Production deployments must leave it off.
- **Configuration.** Secrets come from environment variables. Use a strong,
  shared `JWT_SECRET` different from the development default.
- **SQL injection.** All database access goes through SQLAlchemy expressions and
  bound parameters.
- **Rate limiting / CORS.** These remain the gateway's responsibility.

## 16. Failure recovery and idempotency

### REST idempotency

- Every `POST /payments` requires `Idempotency-Key`.
- The key is unique in the database.
- The stored `request_fingerprint` covers the authenticated user, hold id,
  method, currency and simulated outcome.
- Same key + same request: the original payment is returned (`200`, no new
  charge, no new confirmation).
- Same key + different request: `409`.
- Same hold + a different key: `409` (one payment per hold).
- Keys are scoped by user through the fingerprint; a key cannot reveal another
  user's payment.

### Concurrency

- Two simultaneous requests can both pass the initial lookup and call the
  Reservation Service. After the network call, the service re-checks the key and
  hold before charging.
- The unique indexes on `idempotency_key` and `hold_id` are the final guard: one
  insert wins, the loser is treated as a replay or a `409`.
- A replay waits up to `IDEMPOTENCY_WAIT_SECONDS` for the in-flight payment to
  reach a terminal status. If it is still running, the client receives `409` and
  may retry with the same key.
- This is practical idempotency, **not** a claim of exactly-once processing
  across arbitrary crashes and network partitions.

### gRPC idempotency

- The contract has no idempotency key. `hold_id` is the replay key: a second
  `Charge` for the same hold returns the existing transaction.
- The same database constraints apply.

### Payment succeeds, confirmation fails

- The charge is committed as `SUCCEEDED` **before** the confirmation call.
- A timeout, connection error or 5xx leaves the payment successful with
  `confirmation_status = PENDING` and a safe `confirmation_error`.
- `POST /payments/{payment_id}/retry-confirmation` retries only the confirmation
  using the stored `transaction_ref`; it never creates a new charge.
- A permanently rejected hold (expired/released) is recorded as
  `confirmation_status = FAILED`. There is no automatic refund in that case.

### Reservation Service unavailable before charging

- The request fails with `503` and **no** payment row is inserted.
- The client can safely retry with the same idempotency key.

### Known recovery gap

- A process crash after inserting `PENDING`/`PROCESSING` and before finalising
  leaves the row stuck in that state. There is no background reconciliation
  worker in this implementation. Operationally, detect such rows and either
  retry processing or mark them `FAILED` manually; because no charge was
  confirmed, this does not double-charge a hold.
- `REFUND_PENDING` is transient and moves to `REFUNDED` in the same request. A
  crash in that tiny window leaves it `REFUND_PENDING`; an operator can retry the
  refund endpoint (it will return `409` because the payment is no longer
  `SUCCEEDED`) or repair the row manually.

### 17.4 Frontend / clients

- Send `Idempotency-Key` on every `POST /api/payments` (for example a UUID per
  checkout attempt, reused only for retries of the same request).
- Never send an `amount`; the server rejects it.
- Treat `503` as retryable, and call `retry-confirmation` when the payment is
  `SUCCEEDED` but `confirmation_status` is not `CONFIRMED`.
- Display `confirmation_status`/`confirmation_error` separately from the payment
  status so a successful charge with a pending booking is visible.

### 17.5 Reservation Service contract assumptions

This service assumes the existing Reservation Service behaviour:

- `GET /holds/{hold_id}` returns a JSON object with at least
  `id`, `user_id`, `status`, `total`, and `expires_at` (or `seconds_left`).
- `POST /holds/{hold_id}/confirm` accepts `{"payment_ref": "..."}` and returns
  `200`/`201` on success, `404` for an unknown hold, `410` for an expired hold,
  and `409` for a released/converted hold.
- The same user Bearer token authorises both calls.

The hold response currently has **no currency field**, which is why the REST
request carries the currency and the service validates it against its allow-list
rather than comparing it with the hold.

## Assumptions and limitations of the supplied protobuf contract

- **No idempotency key.** The service uses the unique `hold_id` as the replay
  key. Two logically different checkout attempts for the same hold therefore
  return the first transaction rather than creating a second one.
- **Amount is a client-controlled string.** It is deliberately ignored. The
  authoritative amount is fetched from the Reservation Service.
- **No payment method.** The default is `GRPC_DEFAULT_METHOD` (`CARD`), with an
  optional `x-payment-method` metadata override. This convention is outside the
  contract and must be documented for callers.
- **No user id.** Identity comes solely from the JWT in metadata. There is no
  way for a caller without a user token to charge a hold.
- **No currency on the hold.** Currency is validated against the configured
  allow-list but cannot be compared with the reservation's currency because the
  hold response does not expose one.
- **Statuses and failure reasons are free-form strings.** The service documents
  the six status values; clients should tolerate unknown future values.
- **Double-charge prevention is hold-id-based, not exactly-once.** A crash
  between simulation and finalisation can require manual reconciliation.
- **No schema migrations.** Tables are created at startup with
  `create_all`. A production deployment should introduce Alembic before
  evolving the schema.
- **Refunds do not cancel bookings.** A refund changes only this service's
  payment record. There is no compensation call to the Reservation Service, and
  no real payment provider is involved.
- **gRPC is plaintext by default.** TLS termination is expected at the
  infrastructure boundary; no TLS credentials are configured here.
- **Admin authorization trusts the JWT role claim**, like the other services in
  this repository; it does not call the User Service on every request.
